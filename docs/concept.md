# workOS-Agent — Product Concept

## 1. 한 줄 요약

> **"미리 만들어둔 워크플로 + 요구사항 문서"** 두 가지를 던지면, AI가 워크플로의 각 스텝에 필요한 **태스크들을 자동 분해**해 주고, 사용자는 그 태스크 트리를 **확인 → 실행 → diff 검토 → 커밋** 한다.

---

## 2. 배경 / 문제 정의

- 신규 기능 요구사항이 들어오면 **정해진 패턴**에 맞춰 개발하는 것이 본인의 작업 스타일.
- 최근 AI 에이전트에게 **요구사항 문서 + Swagger + Figma**를 통째로 던지고 결과물만 받는 방식으로 작업하는 경우가 많음.
- 이로 인해 발생하는 문제:
  1. **단계별 품질 편차** — 특정 단계의 결과물 퀄리티가 떨어짐.
  2. **단계별 산출물 부재** — 전체 흐름만 맞추고 중간 산출물이 원하는 형태로 안 나옴.
  3. **오버 엔지니어링** — 본인이 이해하지 못하는 기술이 결과물에 빈번히 섞임.

→ 이를 해결하기 위해 **workOS-Agent 앱** 프로젝트를 진행 중.

---

## 3. 목표 (What to build)

특정 프로젝트마다 **개발 워크플로(파이프라인)를 등록**하고, 각 스텝을 **시각화된 도구로 관리·실행**할 수 있는 앱.

- 스텝마다 요구사항을 적을 수 있어야 함.
- 각 스텝이 참조할 **에이전트/스킬**을 프로젝트 단위 목록에서 선택할 수 있어야 함.
- 스텝 실행 시 **태스크가 자동 생성**되고, **병렬 또는 순차적으로 AI가 작업**.
- 결과물은 **git diff 기반으로 사용자가 검토** 후 커밋.

---

## 4. 핵심 컨셉

| 개념 | 정의 |
|------|------|
| **Workflow (템플릿)** | 프로젝트마다 미리 정의된 스텝 시퀀스. (예: API 분석 → API 개발 → 비즈니스 → UI → 테스트 → 리뷰 → 커밋) 각 스텝은 사용할 에이전트/스킬이 바인딩되어 있음. |
| **Requirement Input** | 사용자가 워크플로에 첨부하는 입력. 요구사항 문서, Swagger, Figma 링크 등. |
| **Task (자동 생성)** | 요구사항을 분석해 각 스텝 아래 N개로 분해된 실제 실행 단위. 각 태스크는 자신만의 좁은 프롬프트를 가짐. |
| **Execution** | 태스크 단위로 병렬/순차 실행. 태스크별로 바인딩된 에이전트/스킬이 좁은 프롬프트로 작동. |
| **Review Gate** | 태스크 완료 후 git diff로 사용자가 변경사항을 검토 → 의미 있으면 커밋. |

## 5. 사용자 시나리오 (End-to-End)

### Phase A. 사전 준비 (1회성)
1. 사용자가 프로젝트별로 **워크플로 템플릿을 등록**.
   - 스텝 목록 정의 (예: API 요구사항 분석 → API 개발 → 비즈니스 → UI → 테스트 → 문서 → 리뷰 → 커밋).
   - 각 스텝에 사용할 **에이전트/스킬을 카탈로그에서 선택**해 바인딩.

### Phase B. 작업 시작
2. 새 작업을 시작할 때 사용자는:
   - 사용할 **워크플로를 선택**.
   - 처리하고 싶은 **요구사항 문서(또는 Swagger 등)를 첨부**.

### Phase C. 태스크 자동 분해
3. 분석 에이전트가 요구사항 문서를 읽고:
   - **어떤 스텝에서**
   - **몇 개의 태스크가 필요한지**
   - 각 태스크의 **좁은 목표(=프롬프트 시드)** 까지 산출.
4. 분해 결과가 **트리 형태로 시각화** 되어 사용자에게 노출.

### Phase D. 검토 & 실행
5. 사용자가 생성된 태스크 트리를 **확인 / 편집 / 승인**.
6. 승인된 태스크들을 **순차 또는 병렬로 실행**.
   - 각 태스크는 **자신의 좁은 프롬프트**가 에이전트에 전달돼 그 태스크만을 위한 작업을 수행.
   - 스텝에 바인딩된 스킬이 컨벤션·패턴을 강제 → 오버 엔지니어링 차단.

### Phase E. 결과 검토 & 커밋
7. 태스크가 끝나면 사용자는 **git diff로 변경 사항을 확인**.
8. 변경이 **유의미하면 커밋** → 다음 태스크/스텝으로 진행.
9. 워크플로 끝까지 반복 → 최종 PR 생성.

## 6. 대표 워크플로 예시 (프론트엔드 신규 기능 개발)

요구사항을 만족하기 위해 워크플로의 각 스텝이 다음과 같이 동작한다.

1. **API 요구사항 분석** — 요구사항을 만족하기 위해 필요한 Swagger 문서 분석, 신규/수정 API 리스트 추출.
2. **API 레이어 개발** — 추출된 API 개수만큼 태스크 자동 생성. API 호출 + React Query 기반 server-state 레이어 개발에 특화된 스킬 사용.
3. **비즈니스 요구사항 분석** — 요구사항 → 도메인 모델·비즈니스 규칙 식별.
4. **비즈니스 로직 개발** — use-case, 도메인 규칙, 검증/계산 로직 구현.
5. **UI 시안 분석** — Figma 시안 분석, 디자인 시스템에 추가가 필요한 컴포넌트 목록 추출.
6. **디자인 시스템 컴포넌트 추가** — 시안에 따라 디자인 시스템에 신규 컴포넌트 등록.
7. **페이지 컴포넌트 추가** — 시안에 맞는 페이지 단위 프레젠테이션 컴포넌트 구현.
8. **기능 조립** — 비즈니스 로직 + 프레젠테이션 컴포넌트 조합해 실제 기능 구현.
9. **테스트 코드 작성** — 추가/수정된 기능에 대한 테스트 작성.
10. **프로덕트 문서 업데이트** — 신규/변경된 기능을 위키/프로덕트 문서에 반영.
11. **코드 리뷰** — 회사 컨벤션을 학습한 코드 리뷰 전문 에이전트가 검수.
12. **커밋 & PR** — 최종 커밋 및 PR 생성.

## 7. 기능 요구사항

| # | 기능 | 설명 |
|---|------|------|
| F1 | **워크플로 템플릿 관리** | 프로젝트별 워크플로 CRUD. 스텝 순서, 스텝별 입력/출력 정의. |
| F2 | **에이전트·스킬 카탈로그** | 프로젝트 단위로 사용 가능한 에이전트/스킬 목록을 관리. |
| F3 | **스텝-스킬 바인딩** | 스텝마다 사용할 에이전트/스킬을 카탈로그에서 선택. |
| F4 | **요구사항 첨부** | 워크플로 실행 시 요구사항 문서·Swagger·Figma 링크 등을 첨부. |
| F5 | **태스크 자동 분해** | 분석 에이전트가 요구사항을 읽고 스텝별 필요한 태스크 N개를 자동 생성 (각 태스크별 프롬프트 시드 포함). |
| F6 | **태스크 트리 시각화 / 편집** | 생성된 태스크를 트리·칸반 형태로 보고 사용자가 편집·승인. |
| F7 | **태스크 실행 (순차/병렬)** | 태스크 단위 실행, 의존성에 따라 직렬·병렬 모드 선택. |
| F8 | **태스크별 좁은 프롬프트** | 태스크 실행 시 해당 태스크만을 위한 좁은 프롬프트가 바인딩된 에이전트에 전달. |
| F9 | **diff 기반 결과 검토** | 태스크 완료 후 git diff UI로 변경 사항 확인. |
| F10 | **선택적 커밋** | 유의미한 변경만 사용자가 커밋. (자동 커밋 X) |
| F11 | **워크플로 진행 상태 대시보드** | 어떤 스텝·태스크가 진행/완료/대기 상태인지 시각화. |
| F12 | **컨벤션 가드** | 스텝에 바인딩된 스킬이 회사 컨벤션·정해진 패턴을 강제해 오버 엔지니어링 방지. |

## 8. 데이터 모델 스케치 (개략)

```
Project
  └─ WorkflowTemplate (1..N)
        └─ Step (ordered)
              ├─ requirements: text
              ├─ inputArtifacts: [doc | swagger | figma | ...]
              └─ boundAgentOrSkill: ref(Catalog)

Project
  └─ AgentSkillCatalog (project-scoped)

WorkflowRun
  ├─ workflowTemplateRef
  ├─ attachedRequirements: [files/links]
  └─ TaskTree
        └─ Task (per step, N개)
              ├─ stepRef
              ├─ scopedPrompt: text   ← 분석 에이전트가 생성
              ├─ status: pending/running/done/failed
              ├─ diff: GitDiff
              └─ commit: ref?
```

## 9. 핵심 설계 원칙

1. **워크플로는 사용자가 만든 템플릿**, AI가 만드는 것은 **태스크 트리**.
2. **태스크 = 좁은 단위 + 좁은 프롬프트** → 단계별 품질 편차·오버 엔지니어링 차단.
3. **모든 단계에 사용자 승인 게이트**: 태스크 분해 후 1회, 각 태스크 diff 검토 1회.
4. **스킬은 회사 컨벤션을 강제**하는 좁은 단위로만 구성한다.
5. **자동화하되 통제권은 사용자에게**.

---

## 10. 비기능 / 설계 관점 메모

- **AI 자율성 ↔ 사용자 통제** 사이의 균형: 모든 스텝 산출물은 사용자 승인 게이트를 거친다(자동 진행 X).
- **스킬은 좁고 명확하게**: 한 스킬 = 한 책임 (예: "Swagger에서 변경 API 추출", "API 메서드 + queryOptions 생성").
- **컨벤션 강제**: 회사 컨벤션·정해진 패턴을 스킬 프롬프트에 내장해 오버엔지니어링/원치 않는 기술 사용 방지.
- **재사용성**: 워크플로 템플릿은 프로젝트 간 복사·import 가능해야 함.
