# 코어 동작 컨셉

## 화면 레이아웃

```
┌──────────────────────────┬──────────────────────────┐
│  좌측: 기능 UI 영역      │  우측: 터미널 영역       │
│                          │                          │
│  - 워크플로우 관리       │  - Claude CLI 실행       │
│  - 태스크 목록 / 실행    │  - 태스크별 새 세션      │
│  - 분해 / 검토 / 편집    │  - 에이전트 작업 진행    │
└──────────────────────────┴──────────────────────────┘
```

- **왼쪽**: 태스크·워크플로우 등 기능을 다루는 UI.
- **오른쪽**: 에이전트(Claude CLI)가 실제로 작업을 수행하는 터미널.

## 실행 플로우 (핵심)

> 사용자가 "이 태스크 실행"을 누르면 다음 순서로 동작한다.

```
[1] UI에서 "기능 실행" 트리거
       │
       ▼
[2] 해당 기능에 대응되는 프롬프트를
    임시(더미) 텍스트 파일로 디스크에 저장
       │   예: /tmp/workos-agent/task-<id>.md
       ▼
[3] 우측 터미널에서 Claude CLI 실행
    (새 세션 — 컨텍스트 격리)
       │
       ▼
[4] 실행 직후, Claude에게
    "그 파일을 읽고 그대로 수행하라"는
    최소 지시만 전달
       │   예: `claude "Read /tmp/.../task-<id>.md and execute it"`
       ▼
[5] Claude가 파일을 읽어 프롬프트 본문을
    스스로 컨텍스트에 적재하고 작업 수행
```

## 왜 이렇게 하나 (설계 근거)

### 1. MCP는 에이전트에게 능동적으로 명령을 보낼 수 없다

- MCP 프로토콜에서 **서버는 클라이언트(에이전트)의 요청에 응답**만 한다. 서버가 먼저 "이 작업을 해라"라고 에이전트에게 명령을 *푸시*할 수 없다.
- 즉, "워크OS가 Claude에게 태스크를 시킨다"는 흐름을 MCP 단독으로는 만들 수 없다.
- **해결책**: 워크OS는 사용자 인터페이스 측에서 **Claude CLI 자체를 새로 띄우고**, 그 시작 인자로 "이 파일을 읽고 실행하라"는 명령을 주입한다. 이렇게 하면 푸시 방향의 명령 흐름이 우회로로 성립한다.

### 2. 긴 프롬프트를 인자로 직접 전달하는 데 한계가 있다

- 분해된 태스크 프롬프트에는 컨텍스트(파일 경로, 검수 체크리스트, 도메인 규칙 등)가 누적되어 **수 KB 이상으로 커지기 쉽다**.
- 셸 인자/터미널 입력으로 그대로 흘려보내면 **이스케이프·길이 제한·가독성** 문제가 발생한다.
- **해결책**: 프롬프트 본문은 **파일에 저장**하고, 터미널에는 "그 파일을 읽으라"는 짧은 지시만 전달. Claude는 파일 읽기에 최적화돼 있으므로 임의 길이의 컨텍스트를 안정적으로 수용한다.

### 3. 매 태스크마다 새 세션을 강제할 수 있다

- 파일 + 새 CLI 인스턴스 조합 자체가 **세션 격리**를 자연스럽게 보장한다.
- 이전 태스크의 컨텍스트가 다음 태스크로 흘러들지 않아 **컨텍스트 오염 차단** 목표(→ [PRD](./PRD.md))가 달성된다.

## 한 줄 요약

**"워크OS는 태스크 프롬프트를 임시 파일에 쓰고, 우측 터미널에서 Claude CLI를 새로 띄우면서 그 파일을 읽게 만든다 — MCP가 에이전트에게 명령을 푸시할 수 없는 한계와, 긴 프롬프트를 인자로 흘려보낼 수 없는 한계를 동시에 우회한다."**
